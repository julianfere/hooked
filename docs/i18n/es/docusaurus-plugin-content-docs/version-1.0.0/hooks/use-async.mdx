# useAsync

Gestiona el ciclo de vida completo de una función asíncrona — idle, pending, fulfilled y rejected — con cancelación automática y ejecución opcional al montar.

:::danger Cambio incompatible en 1.0
El `AbortSignal` ahora es el **primer** argumento de `fn`, seguido de los argumentos que le pasás a `trigger`. En 0.x se agregaba como último argumento. Mirá la [guía de migración](../migration/v1.mdx#useasync-signal-first).
:::

## Firma

```ts
type AsyncFunction = (signal: AbortSignal, ...args: any[]) => Promise<any>;

function useAsync<F extends AsyncFunction>(
  fn: F,
  options?: UseAsyncOptions<Awaited<ReturnType<F>>>
): {
  trigger: (...args: TriggerArgs<F>) => Promise<void>;
  reset: () => void;
  status: "idle" | "pending" | "fulfilled" | "rejected";
  data: Awaited<ReturnType<F>> | undefined;
  error: unknown;
  loading: boolean;
};
```

`TriggerArgs<F>` son todos los parámetros de `fn` que vienen después del signal. Los parámetros opcionales siguen siendo opcionales.

## Opciones

| Propiedad | Tipo | Por defecto | Descripción |
|-----------|------|-------------|-------------|
| `immediate` | `boolean` | `false` | Ejecuta `fn` automáticamente al montar. Solo para funciones que no reciben argumentos además del signal |
| `onSuccess` | `(data: T) => void` | — | Se llama cuando la promesa se resuelve |
| `onError` | `(error: unknown) => void` | — | Se llama cuando la promesa es rechazada |

## Valor de retorno

| Propiedad | Tipo | Descripción |
|-----------|------|-------------|
| `status` | `"idle" \| "pending" \| "fulfilled" \| "rejected"` | Estado actual del ciclo de vida |
| `data` | `T \| undefined` | Valor resuelto, o `undefined` |
| `error` | `unknown \| undefined` | Razón del rechazo, o `undefined` |
| `loading` | `boolean` | `true` mientras `status === "pending"` |
| `trigger` | `(...args) => Promise<void>` | Ejecuta la función asíncrona con los argumentos dados |
| `reset` | `() => void` | Cancela la request en vuelo y vuelve el estado a `idle` |

## Comportamientos clave

- `fn` recibe un `AbortSignal` como **primer argumento**. Pasáselo a `fetch` (o a cualquier API cancelable) para tener cancelación automática. Si tu función no lo necesita, podés omitir el parámetro.
- Los argumentos de `trigger` se pasan después del signal: `trigger(id, page)` llama a `fn(signal, id, page)`.
- Volver a disparar mientras hay una request en vuelo cancela la anterior automáticamente; solo se guarda el último resultado.
- La request en vuelo se cancela al desmontar el componente.
- `fn`, `onSuccess` y `onError` pueden ser funciones inline: siempre se usa la última versión.

## Pasar argumentos

```tsx
import { useAsync } from "@julianfere/hooked";

function TarjetaUsuario() {
  const { data, loading, trigger } = useAsync(
    (signal, id: string, incluirPosts?: boolean) =>
      fetch(`/api/usuarios/${id}?posts=${incluirPosts ?? false}`, { signal }).then(
        (res) => res.json() as Promise<Usuario>
      )
  );

  return (
    <>
      <button onClick={() => trigger("42")}>Cargar usuario</button>
      <button onClick={() => trigger("42", true)}>Cargar usuario con posts</button>
      {loading ? <p>Cargando…</p> : <p>{data?.name}</p>}
    </>
  );
}
```

## Cuándo usar las APIs de React 19

React 19 trae primitivas que cubren algunos casos que antes resolvía `useAsync`. Preferilas cuando encajen:

| Caso de uso | Recomendado |
|-------------|-------------|
| Leer datos durante el render con Suspense y error boundaries | [`use(promise)`](https://react.dev/reference/react/use) |
| Envíos de formularios y mutaciones con estado pendiente | [`useActionState`](https://react.dev/reference/react/useActionState) / [`useTransition`](https://react.dev/reference/react/useTransition) |
| Requests imperativas disparadas por eventos, con cancelación y callbacks, sin Suspense | `useAsync` |
